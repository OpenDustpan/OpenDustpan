# 253. Dev data does not reach a production installation

Status: accepted · 2026-10-19. The project owner decided it. Applies ADR 250 to the restore of a backup from a dev installation. Extends ADR 252 decision 7.

## Context

`opendustpan dev` signs in through the stored person `dev:admin`, which holds the site-administrator role (ADR 252). A backup leaves the installation table out. A restore keeps the live installation kind. So an operator can restore a backup of a dev installation into a production installation. The restore then brings `dev:admin`, its grant, and maybe its sessions and tokens.

ADR 252 decision 7 closes the sign-in side. A production server refuses to authenticate a principal with the prefix `dev:`. That is one layer. ADR 250 requires more layers, and each layer must stop the attack alone. This ADR adds two layers before the data arrives. One layer is a refusal at the restore. The other is a strip of the staged data. A third check, inside the swap, does not rely on either layer.

No OpenDustpan installation exists yet outside CI. So no backup without an installation kind needs handling.

## Decision

1. **A backup records the kind.** The manifest has the key `installationKind`. Its value is `dev` or `production`. The key is required. The backup export reads the kind from its own database through `backup.KindReader`. It does not accept a kind from the caller. When the database claims no kind, or the stored value is not a known kind, the export fails with `installation.ErrUnavailable` and writes no backup. The interface lives in `pkg/backup`, which uses it. The package `installation` keeps the `Kind` type. `KindReader` is separate from `installation.KindStore` because `ReadKind` must never claim a kind.
2. **The manifest format number rises** from 2 to 3. The existing format check refuses a manifest of format 2. A manifest of format 3 with no kind, or with an unknown value, is not valid. The parse uses `installation.ParseKind`. The restore refuses it with `backup.ErrManifestKindInvalid`. There is no conversion and no compatibility path. The restore pins `installationKind` with the other manifest fields (`pinnedManifest`). The check before the apply step (`repinManifest`) refuses a backup whose kind changed after the first check.
3. **The manifest is not authenticated.** A person who can write to the backup target can change `installationKind`. So the kind in the manifest is a claim, and it is never the only input. On a production installation, the restore decides from the staged data (decision 6).
4. **Layer 1: refuse by default.** A production installation refuses to restore a backup of the kind `dev`. The error is `backup.ErrDevBackupRefused`. The API answers with status 409. One exception exists: the server started with the flag in decision 7. Four independent checks apply:
   - The parse of the manifest refuses a missing or unknown kind.
   - The restore service compares the kind of the backup with the kind of the live installation. It does this before it enters maintenance mode and before it takes the backup of the live data.
   - The stage call of the store adapter gets `backup.StageOptions`, with the claimed kind of the backup and the `AllowDev` value. It compares them with the live kind that it reads from its own database, and it refuses before it loads a row. `StagePortable` of `backup.PortableStager` takes `StageOptions` as its last parameter. The design change adds the parameter and updates both adapters and the `storetest` call sites. The adapters ignore the value until the implementation change. No separate interface exists, so a caller cannot skip the check.
   - The staged data decides (decision 6). A manifest of the kind `production` that holds dev people is refused too.

   The check-only restore runs the same checks. So it reports the refusal and changes nothing. A dev installation restores a dev backup as before.
5. **A production backup into a dev installation does not change.** A dev installation is the less trusted side. It holds no real people, and the person who runs it holds its data. The refusal protects the production side only. The answer carries an info warning with the code `production-backup-into-dev`: "This backup is from a production installation. Its tokens and sessions are now in a dev data directory."
6. **Layer 2: strip at the restore.** On a production installation, the strip and the check run on every restore. The staged data decides, not the kind in the manifest. The steps are:
   - After the stage step and its count checks, the service calls `DevStripper.StripDevStaged` with `DevStripDetect`. It never touches a live table.
   - Dev rows in the staging area and the flag off: the restore refuses with `ErrDevBackupRefused`, discards the staging area and changes nothing. This is the fail-closed case for a manifest that says `production`.
   - Dev rows and the flag on: the service calls it with `DevStripRemove`, then proves that the staged data holds none. A failure returns `ErrDevStripIncomplete`: the restore discards the staging area and the live data stays unchanged.
   - No dev rows and a manifest of the kind `dev`: the flag rules of decision 4 apply, and the strip removes nothing.

   The apply step is the one atomic swap of the restore. So the live data never holds a dev principal from the backup. The strip removes these classes:
   - principals with a subject that starts with `dev:`, in any ASCII letter case,
   - their grants, group memberships, sessions, access tokens and open sign-in requests,
   - `temp_admins` rows, matched by `principal_id` of a removed principal and by `subject` that starts with `dev:`,
   - sign-in providers with the reserved provider ID `dev`,
   - the dev subject in `Approvers.Users` of the approval rules, the approval defaults and the ownership rules in `gate_objects`. The strip matches each entry by the matching rule of decision 7. `Approvers.Groups` and `Approvers.UnitOwners` are not subjects, so they stay. The rule stays too. Decision 17 says what happens when the strip removes the last approver,
   - dangling data. This is grants, group memberships, sessions and tokens that name a principal that does not exist. It is also rows that name a subject with the prefix and have no principal row.

   The strip does not trust the foreign keys of the staged data. The data may already be wrong in the backup. The strip does not remove audit entries, so the audit chain stays whole. `gate_records` keeps the decision records. They are history, like audit entries, and they grant no authority. A column in another table can store the subject of a dev principal as text, for example "created by". That text stays as history and grants no authority. The strip and the check do not read it.

   A coverage test lists every column that refers to a principal. It lists the fields in JSON bodies too, not only columns. It includes `temp_admins` and every `gate_objects` field that names approvers or owners by subject, for the kinds `approval-rule`, `approval-default` and `ownership-rule`. It also lists the Cedar text of access limits and of the `Unless` of a gate. The strip does not edit Cedar text. After the strip, no principal matches a dev subject, and the sign-in refusal of decision 13 stops a dev principal from coming back. So the Cedar text grants no authority to a dev person. For each column and field, the test says if the strip removes it or keeps it, and why. It fails when a new column or field appears.

   **One rule for both swap paths.** The strip and the swap-time check of decision 12 always cover the whole staging area. This is true for a restore with the access tables and for a restore with `KeepAccessTables` (a caller without `server:restore-access`). `DevStripper` has no option for a part of the staging area. On the path with `KeepAccessTables`, the swap does not take the staged access tables, but the strip and the check still read them. A staging area with a dev principal is refused or stripped on both paths. Layer 1 applies to both paths too.

   **`temp_admins` on the path with `KeepAccessTables`.** The swap keeps the live access tables. It takes `temp_admins` from the backup. The strip stays free of the path. It removes the staged rows that match by `subject` with the matching rule of decision 7. It does not judge a row by its `principal_id` against the staged `principals`. The swap, `ApplyStagingKeepingAccess`, drops each staged `temp_admins` row that names a `principal_id` that the live `principals` table does not hold. It does this in its swap transaction, after it put the live principals into the staged data. It returns the count in `KeepAccessResult.DroppedTempAdmins`. The restore service adds the count to the class `temp-admins` of the report and stores the report again after the swap.

7. **The matching rule.** One rule matches a dev subject everywhere: the first 4 bytes, ASCII case-insensitive, equal to `dev:`. This is `principal.IsDevSubject`. Both adapters match in SQL with the same rule, and only the ASCII letters fold. A non-ASCII look-alike does not match. A subject `dev` with no colon does not match.
8. **The flag.** The flag is `--unsafe-allow-restoring-dev-installation-backups-into-production`. The package `cmd/opendustpan` owns the name. It follows the pattern of the other long override flags (ADR 124). It is a flag of the command line only. It has no environment variable, no entry in the configuration file, and no setting in the API. The settings layers of ADR 63 never set it. The server writes one warning to the log at each start with the flag. The audit entry of a restore records whether the flag was on.

   The SDK has a bool: the field `AllowDevBackups` of `backup.RestoreConfig`, set through the option `dustpan.WithAllowDevBackups(bool)`. The default is false. An embedder sets it in Go code only. The field `AllowDevHint` holds the words that the refusal text uses to name how to allow it. `cmd/opendustpan` passes the flag in code quotes. An embedder passes its own words, or an empty string, and the sentence is left out.
9. **Refusal and warning text.** The text is strict STE. The refusal: "This installation is a production installation. The backup is from a dev installation. We do not recommend this restore. To restore it, start the server with `--unsafe-allow-restoring-dev-installation-backups-into-production`." The warning after a restore with the flag: "This restore removed the dev users and their grants. Things that depend on them may break. We do not recommend this restore." The answer to `POST /api/server/restores` and to `GET /api/server/restores/{id}` carries a `warnings` list of `{code, text}` entries, with the code `dev-backup-into-production`. The manifest read shows `installationKind`. So a client can warn before the person accepts. The CLI reads the manifest first. It prints the warning before it starts the restore. A check-only restore reports the counts that it would remove.
10. **Untrusted subjects are cleaned before they are written.** A subject comes from the backup, so it is untrusted. A subject reaches an audit entry, the restore record, a log line or an API answer. Before that, the code removes CR, LF and every other control character. It cuts the subject to 255 bytes, the length of a subject made through the API. It marks a cut with a flag in the entry. Both the strip and the sign-in denial use this one function.
11. **Record each removal, with a bound.**
    - The restore service writes the removal report into the restore record before the swap (`backup.DevReportRecorder`). The `restores` table survives the swap. Adding the column is a new numbered migration in the implementation change.
    - After the swap, it writes the audit entries that survive the swap. It writes one entry for each removed principal, up to 100 principals. It writes one summary entry with the number of the other principals and the sum of their counts. It writes one entry for each class that has no principal (providers, gate approvers and dangling data).
    - The strip logs one warning for each class that removed rows, with the count and never a token or a session ID.
    - If an audit append fails, the restore still ends as finished. The answer carries a warning with the code `audit-append-failed`, and the server logs an error. The swap already happened, and the report is in the restore record.
12. **Layer 3a: the swap refuses dev data.** The apply step of the store adapter works in the swap transaction. It reads the live installation kind from its own database. If it cannot read the kind, it refuses the swap and changes nothing. On a production installation, it checks the whole staging area in that transaction, on both swap paths. The steps are `ApplyStaging` and `ApplyStagingKeepingAccess`. It refuses the swap with `ErrDevBackupRefused` when the staging area holds a dev principal. It refuses it too when a row names one. This check does not read the options of the stage call, the manifest or the report of the strip. It stops the swap if the strip has a defect.
13. **Layer 3b: refuse at sign-in.** The rule of ADR 252 decision 7 stays. A production server refuses to authenticate a session or a token whose principal has a subject that starts with `dev:`. The start logs one warning. A refused dev sign-in writes one denial record through the existing server audit path. The writer limits it to one record for each principal for each hour, with the count of the refusals since the last record. The table of the limiter has a size cap. The shared denial mechanism for refused requests replaces this record when it lands.
14. **Documentation.** The implementation change adds the restore guide text, with the warning and the flag. It adds the flag to the generated configuration reference as a `Setting` with `Env` set to `""` and `File` set to `""`.
15. **Layers and tests.** Each layer has its own test. The test sends hostile input to that layer alone (ADR 250 decision 4). The tests of the stage, the swap and the strip run on SQLite and on PostgreSQL. One shared table of subjects feeds the SQLite match, the PostgreSQL match and `principal.IsDevSubject`. The table has `dev:admin`, `DEV:`, `Dev:Admin`, `dEv:`, non-ASCII look-alikes, `dev` with no colon and `de` and the empty string. All three must agree.

16. **The restore needs the dev ports.** `backup.RestoreLive` holds `KindReader`, `DevStripper` and `DevReportRecorder`. The compiler refuses a restore service over a live store that lacks one of them. With a backup target, the server wiring checks the namespace store with a type assertion to `backup.RestoreLive` (`newRestoreService` in `pkg/dustpan`). A store that lacks a port gets a start error, `errRestoreNeedsLive`, and the text names each missing port. The server does not start. A production restore never skips the strip, the report or the kind check because a port is missing. The server has no fallback that runs a restore without the ports. The test is `TestNewRestoreServiceNeedsDevPorts` in `pkg/dustpan`. It builds a store that has the restore ports of before. The store lacks `KindReader`, `DevStripper` and `DevReportRecorder` in turn. The test expects the start error that names the missing port. A second test, `TestServerWithoutDevPortsDoesNotStart`, expects that `NewServer` fails for such a store.
17. **Approval rules after the strip.** Four rules apply to approvers.
    - **The value that nobody can meet.** The package `gate` has the constant `NoApprover`, with the value `!no-approver`. A subject that starts with `!` is not valid (`principal.ValidateSubject`). So no principal made through the API has it. The approval code never counts a signature whose subject equals `NoApprover`, also not for a principal that an identity provider made. So this value is valid stored data that nobody can meet.
    - **The strip never leaves an empty list.** The strip can remove the last approver of a rule or a default. This is true for an approval rule, an approval default and an ownership rule. Then it replaces the list with `Users: [NoApprover]`. It writes a report entry in the class `approvers` that names the object. An approval default with no approvers from the start means "any holder of the approve action who is not the author". The strip does not change such a default, because it removed nothing. But a default that lost its last approver does not become that open default. Without this rule, the strip would widen the approval.
    - **The gate refuses.** A stored rule in enforce mode can have only `NoApprover` as its approver. This is true for an approval rule, an approval default and an ownership rule. Then the gate refuses the change that the rule covers. It does not skip the requirement. It does not fail the whole scope with an error. The requirement stays open until a person changes the rule. A stored approval rule or ownership rule with an empty approver list is read the same way, as `Users: [NoApprover]`. An approval default keeps its meaning for an empty list. The test is `TestGateRefusesRuleWithoutApprover`.
    - **No dev signatures.** On a production installation, the approval code never counts a signature whose subject is a dev principal. The code uses the matching rule of decision 7. This holds when the signature is in the data already. So a decision record or an open request from a backup cannot give an approval to a dev person. The test is `TestApprovalIgnoresDevSignatureInProduction`.

## Consequences

- The manifest format number changes. Every backup made before this change is invalid for the restore. No installation outside CI exists, so no one loses data.
- A restore of a dev backup into production needs a restart of the server with a long flag. An operator who needs it types the flag at each start, and the log warns at each start.
- The strip may break what depends on the dev people, for example a job that a dev person owns. An approval rule can have no approver left. The strip then replaces the list with `NoApprover`, and the gate refuses the change that the rule covers until a person changes the rule. The warning says so. We advise against the restore.
- A new table that refers to a principal needs an entry in the coverage test of the strip. The test fails until the author decides to remove or to keep the rows.
- The audit log holds at most 100 entries of principals and 1 summary entry for one restore, so a hostile backup cannot flood it. The restore record holds the same bounded report.
- The console shows the warning in its restore flow. A follow-up issue in the console repository tracks it.

# Postmortem: Pulumi CLI 3.273.0 breaks the console URL steps of the e2e suite

Date of the event: 2026-10-29. Date of this record: 2026-10-30.
Status: draft. Severity: low. No user data or user-visible server behavior
was affected.

This record is blameless. It asks what the process did, not who did it. The
"latest" entry of the e2e matrix did its job: it found a change in the Pulumi
CLI one nightly run after the release. The goal is to make that signal faster
and clearer.

## Summary

Pulumi CLI 3.273.0 prints a shorter console link in the output of
`pulumi login`. Before, the link ended with the user name. Now it is the
console root. The e2e steps `console url from api. host` and
`console url from PULUMI_CONSOLE_DOMAIN` expected the old text, so they
failed. The change is deliberate and upstream. The server did not change and
needs no change. Only the assertions need an update.

Each fact has a mark. **Fetched** means that the author read it from the

## What changed in the CLI, and why

Fetched, from the Pulumi `CHANGELOG.md`, entry `3.273.0 (2026-10-28)`,
section Bug Fixes:

> [backend/service] Link to the Pulumi Cloud console root instead of a page
> named after the user in `pulumi login`, `pulumi whoami --verbose`, and
> `pulumi about`, so the link no longer opens a Not Found page for users
> without an organization of that name [#25305]

Findings:

- The change is **deliberate**. It is listed as a bug fix, with a reason.
  It is not a regression.
- The old link was `<console>/<user name>`. The new link is `<console>`.
  The failing output in the nightly log is
  `Logged in to http://api.dustpan.test as admin (http://app.dustpan.test)`.
  The test expected `(http://app.dustpan.test/admin)`.
- Both console URL steps fail the same way, on SQLite and on PostgreSQL in the
  `TestCLIs` matrix. The `PULUMI_CONSOLE_DOMAIN` step now also prints the
  root, so the expected `https://console.example.test:3000/admin` is wrong
  there too.
- The author did not read the source of upstream pull request 25305. The
  statement that the CLI builds the link from the backend URL and not from an
  answer of the server comes from the e2e test (its comment, and the
  `PULUMI_CONSOLE_DOMAIN` override step). It is an inference, not a fetched
  fact.

Does the server need a change? **No.** Search of the Go code of the server
finds no field that carries a console URL in the answers of the Pulumi
Cloud-compatible API. The e2e step names the source of the link as the backend
URL host (`api.` to `app.`) or the `PULUMI_CONSOLE_DOMAIN` variable. Only the
two assertions need an update.

## Impact

- **Users of OpenDustpan:** the server sent the same answers before and after.
  A user of 3.273.0 sees the console root in the `pulumi login` line instead
  of a link that ends with the user name. The author found no functional
  difference: the line is information for a person, and the CLI does not use
  it to talk to the server. Not fetched: a check of the real CLI source, and a
  check of what the OpenDustpan console shows at the old path. The user name
  path is a page that Pulumi Cloud has. The OpenDustpan console may not.
- **Project:** the nightly run was red for a second reason (see below). Pull
  requests were not blocked, because no non-draft pull request ran the `e2e`
  job after the release. A pull request that became ready would have failed
  on the same four steps.
- **Release gate:** none was affected, because no release was in progress.
  Not fetched: the release workflow, so the author cannot say if it runs the
  "latest" entry.

## What went well

- The matrix entry `latest` found the change at the first run that could. The
  entry downloads the newest version at each run, so no person had to add it.
- The failure is precise: file and line, the expected text and the real text
  are in the log.
- The pinned entries (3.250.0 and 3.200.0) did not fail. This shows that the
  change is in the new CLI and not in the server.
- The failure had a clear cause in the upstream changelog. The change was easy
  to find.

## What could be better

1. **A known red run hides a new red cause.** Run 2 and run 3 of the nightly
   job were both red because of `TestDriftAPI` (the test needs the in-process
   server and the nightly job uses the binary). The new failure joined an
   already red run. GitHub sends one notice for a failed scheduled run, so a
   person who saw red on 2026-10-28 had no new signal on 2026-10-29. The
   `TestDriftAPI` failure is a separate problem, and it is the first thing
   that a person has to fix to get a clean signal.
2. **One job holds all causes.** The nightly job runs the full suite as one
   step. A failure of a "latest" CLI looks the same as a failure of the
   server. A person must read the log to tell them apart.
3. **Pull requests do not run the nightly job, and drafts run no jobs.** The
   first real check of a new CLI release can be a nightly run. A new CLI
   release, the Pulumi CLI or OpenTofu, can also make an unrelated pull
   request red the day it is ready. The reviewer of that pull request then
   has to find out that the cause is not their change.
4. **We learn of a CLI release late and by accident.** The suite looks up the
   newest version only when it runs. No job tells us "a new version exists".
5. **The assertion checks an exact string.** The step expects the whole link,
   including a path that the CLI is free to change. The meaning that the step
   is meant to record is: the CLI derives the console host from the backend
   URL, or from `PULUMI_CONSOLE_DOMAIN`. The path after the host is not part
   of that meaning.
6. **There is no written policy** for when a new CLI version joins the pinned
   matrix, and for who looks at a red "latest" entry. The matrix is "newest
   plus older pinned entries" in `e2e/tool.go`. How a version moves from
   "latest" to a pin is not written down.
7. **OpenTofu has the same shape.** `OpenTofu()` in `e2e/tool.go` also has a
   `latest` entry. The same gaps apply. The author did not check the OpenTofu
   result of the runs above (not fetched).

## Durable compatibility plan

The owner asked if the server can make every supported Pulumi version print
the same correct console link. The answer from the upstream source is **no**,
and the server needs no change. Facts below are from the source of the tags
v3.272.0 and v3.273.0. Coverage is partial: the pages were large and the
reader saw only part of each file (marked where it matters).

- **Fetched:** in 3.272.0, `cloudBackend.URL()` called `CurrentUser()` and added
  the user name to the console link. The user name came from the answer of
  `GET /api/user`. So the server did influence the old link.
- **Fetched:** in 3.273.0, `URL()` returns `client.CloudConsoleURL(b.url)`. It
  no longer asks for the user name. The base URL `b.url` comes from the
  `PULUMI_API` variable, the stored credentials or the backend URL on the
  command line. It does not come from a server answer.
- **Not fetched:** the definition of `client.CloudConsoleURL`, the code that
  prints "Logged in to", and the `PULUMI_CONSOLE_DOMAIN` handling.
- **Result:** after 3.273.0 no field of any server answer can add the path to
  the link. Older versions already print the link with the user name, and our
  `/api/user` answer is correct for them. A server change cannot make the two
  link shapes equal. Do not add a server change for this. It would add a rule
  with no effect.

What keeps the server and the suite compatible over time:

1. **A table and a contract test** (issue #2055). Record the fields that each
   CLI version reads from each answer. Test that the server sends them in that
   shape. A new CLI that reads a new field fails this test first.
2. **A scheduled run against each new release.** The nightly run finds a new
   version by chance (#2049). The daily check of #2050 finds it on the day and
   opens one issue.
3. **A rule for the matrix** (#2051). A new minor version of a tool runs as
   "latest" first. A person reads its changelog for login, state and lock
   changes. After one clean week it becomes a pin, and the oldest pin leaves.
4. **Assertions that check meaning** (#2047). Output text that the CLI owns
   is not part of the contract.
5. **OpenTofu** (#2052). The review is done and found no cause for concern:
   - **Fetched:** the nightly run of 2026-10-29 ran OpenTofu 1.13.2 (in
     `TestBothToolsSameServer`). The log has no failed `TestCLIs/opentofu`
     step in that run.
   - **Fetched:** release dates from the GitHub releases page of OpenTofu: 1.12.8
     on 14 October, 1.12.9 and 1.13.2 on 21 October. The newest release is
     1.13.2. 1.13.0 and 1.13.1 came on 30 September and 1 October.
   - **Fetched:** the changelogs of 1.13.0, 1.13.1, 1.13.2, 1.12.8 and 1.12.9
     have no entry about the cloud block, the HTTP backend, TFE, login, locks,
     state upload or download, or service discovery. The entries that touch
     workspaces (1.13.0 #4428, 1.13.2 #4706) change only CLI text and
     shell completion. Two entries are security fixes (1.12.8 #4700, 1.12.9
     #4751).
   - **Result:** no test change is needed for OpenTofu. The gaps of items 1 to 4
     apply to it in the same way.

Because no server change is possible, there is no second pull request for the
server.

## Lessons

- A "latest" entry is a feature, not a flake. Keep it.
- A deliberate upstream change needs a change in our test. It does not
  need a change in the server. Say so in the first line of the fix, so a
  reviewer does not look for a server bug.
- A signal is only as good as the run around it. A run that is red for one
  known reason cannot show a second reason.

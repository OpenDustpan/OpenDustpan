# Postmortem: Pulumi CLI 3.273.0 breaks the console URL steps of the e2e suite

Date of the event: 2026-10-29. Date of this record: 2026-10-30.
Status: draft. Severity: low. No user data and no server behavior changed.

This record is blameless. It asks what the process did, not who did it. The
"latest" entry of the e2e matrix found a change in the Pulumi CLI in the first
nightly run after the release. The goal is to make that signal faster and
clearer.

## Summary

Pulumi CLI 3.273.0 prints a shorter console link in the output of
`pulumi login`. Before, the link ended with the user name. Now it is the
console root. The e2e steps `console url from api. host` and
`console url from PULUMI_CONSOLE_DOMAIN` expected the old text, so they
failed. The change is deliberate and upstream. Before 3.273.0 the CLI took the
user name for the link from the answer of `GET /api/user`. The server sent a
correct answer then and now. The server needs no change. Only the assertions
needed one.

## What changed in the CLI, and why

Fetched, from the Pulumi `CHANGELOG.md`, entry `3.273.0 (2026-10-28)`,
section Bug Fixes:

> [backend/service] Link to the Pulumi Cloud console root instead of a page
> named after the user in `pulumi login`, `pulumi whoami --verbose`, and
> `pulumi about`, so the link no longer opens a Not Found page for users
> without an organization of that name [#25305]

Fetched, from the source of the tags v3.272.0 and v3.273.0 (partial reads of
`pkg/backend/httpstate/backend.go`):

- In 3.272.0, `cloudBackend.URL()` called `CurrentUser()` and added the user
  name to the console link. The user name came from `GET /api/user`. So the
  server answer did influence the old link.
- In 3.273.0, `URL()` returns `client.CloudConsoleURL(b.url)`. It does not ask
  for the user name. The base URL `b.url` comes from the `PULUMI_API`
  variable, the stored credentials or the backend URL on the command line. It
  does not come from a server answer.
- Not fetched: the definition of `client.CloudConsoleURL`, the code that prints
  "Logged in to", and the `PULUMI_CONSOLE_DOMAIN` handling.

Findings:

- The change is **deliberate**. It is listed as a bug fix, with a reason. It
  is not a regression.
- The old link was `<console>/<user name>`. The new link is `<console>`. The
  failing line in the nightly log is
  `Logged in to http://api.dustpan.test as admin (http://app.dustpan.test)`.
  The test expected `(http://app.dustpan.test/admin)`.
- Both console URL steps failed the same way on SQLite and on PostgreSQL in the
  `TestCLIs` matrix. The `PULUMI_CONSOLE_DOMAIN` step also printed the root,
  so its expected text `https://console.example.test:3000/admin` was wrong too.
- The pinned entries (3.250.0 and 3.200.0) did not fail.

Does the server need a change? **No.** After 3.273.0 no field of any server
answer can add the path to the link. Older versions print the link with the
user name, and our `/api/user` answer is correct for them. A server change
cannot make the two link shapes equal. It would add a rule with no effect.

## The 401 from GET /api/user

The first contract check (pull request #2070) listed one "new read" of 3.273.0:
`GET /api/user` with the status 401. The author checked it with the
repository's own e2e reports.

- **Fetched:** in the reports of the whole suite, the 401 comes from the step
  `import with wrong token`. The step in `e2e/e2e_test.go` runs
  `pulumi stack import` with `PULUMI_ACCESS_TOKEN=importWrongToken` and
  `Fail: true`. It is a deliberate negative test.
- **Fetched:** the same 401, from the same step, is in the reports of 3.200.0,
  3.250.0 and 3.273.0. It is not new in 3.273.0.
- **Cause of the false "new read":** the contract files were first written from
  a run of `TestCLIs` alone. The comparison read the reports of the whole
  suite, which include the import test. #2070 now reads only the reports of the
  `TestCLIs` scenario.
- **Limit:** the recorder does not store the `Authorization` header, so the
  author could not show the header of that one request. The evidence is the
  code of the step, and the same 401 for all three versions.
- **Result:** no server change. The server answered 401 to a wrong token.

## Impact

- **Users of OpenDustpan:** the server sent the same answers before and after.
  A user of 3.273.0 sees the console root in the `pulumi login` line instead
  of a link that ends with the user name. The author found no functional
  difference in the CLI: the line is information for a person. Not fetched: a
  check of what the OpenDustpan console shows at the old user name path.
- **Project:** the nightly run was red for a second reason (see below). Pull
  requests were not blocked, because no non-draft pull request ran the `e2e`
  job after the release. A pull request that became ready would have failed on
  the same four steps.
- **Release gate:** none was affected, because no release was in progress. Not
  fetched: the release workflow, so the author cannot say if it runs the
  "latest" entry.

## What went well

- The matrix entry `latest` found the change in the first run that could. The
  entry downloads the newest version at each run, so no person had to add it.
- The log names the place of the failure: `harness.go:2179`, the expected text
  `(http://app.dustpan.test/admin)` and the real text
  `(http://app.dustpan.test)`.
- The pinned entries did not fail. This shows that the change is in the new CLI
  and not in the server.
- The upstream changelog has an entry with a reason for the change.

## What could be better

1. **A known red run hides a new red cause.** Run 2 and run 3 of the nightly
   job were both red because of `TestDriftAPI` (the test needs the in-process
   server and the nightly job uses the binary). The new failure joined an
   already red run. GitHub sends one notice for a failed scheduled run, so a
   person who saw red on 2026-10-28 had no new signal on 2026-10-29.
2. **One job holds all causes.** The nightly job runs the full suite as one
   step. A failure of a "latest" CLI looks the same as a failure of the
   server. A person must read the log to tell them apart.
3. **Pull requests do not run the nightly job, and drafts run no jobs.** The
   first real check of a new CLI release can be a nightly run. A new release of
   the Pulumi CLI or OpenTofu can also make an unrelated pull request red the
   day it is ready. The reviewer then has to find out that the cause is not the
   change.
4. **We learn of a CLI release late and by accident.** The suite looks up the
   newest version only when it runs. No job tells us that a new version exists.
5. **The assertion checked an exact string.** The step expected the whole link,
   including a path that the CLI is free to change. The step records where the
   CLI takes the console host from: the backend URL or
   `PULUMI_CONSOLE_DOMAIN`. The path after the host is not part of that.
6. **There is no written policy** for when a new CLI version joins the pinned
   matrix, and for who looks at a red "latest" entry. The matrix is "newest
   plus older pinned entries" in `e2e/tool.go`.
7. **OpenTofu has the same shape.** `OpenTofu()` in `e2e/tool.go` also has a
   `latest` entry. The same gaps apply. The review below found no problem in
   its recent releases.

## Durable compatibility plan

The question was: can the server make every supported Pulumi version print the
same correct console link? The answer is **no**, for the reasons in the section
"What changed in the CLI, and why". The plan keeps the server and the suite
compatible with new CLI releases in other ways.

1. **Contract files and a check** (issue #2055, pull request #2070). For each
   tested CLI version, a file holds what the server sent to the real CLI in the
   e2e run: the routes, the statuses, the fields that every answer had
   (including error answers) and the response header names. The suite fails if
   a version with a file loses one of them. **Limit:** a file does not show
   which fields the CLI reads. It shows what the server sent when the CLI
   worked. It does not hold the type or value of a field, the request, the
   fields of an answer longer than 4096 bytes, or the order of requests.
   `e2e/doc.go` lists this. A new CLI version has no file. The run lists what
   it has that the newest file does not have, in `contract.md`.
2. **A scheduled run against each new release.** The nightly run finds a new
   version by chance (#2049). The daily check of #2050 finds it on the day and
   opens one issue. It does nothing until the contract files of item 1 exist.
3. **A rule for the matrix** (#2051). A new minor version of a tool runs as
   "latest" first. A person reads its changelog for login, state and lock
   changes. After one clean week it becomes a pin, and the oldest pin leaves.
   This is a proposal. The owner decides.
4. **Assertions that check meaning** (#2047, pull request #2074). The console
   link steps check the scheme and the host, and let the path be either none or
   the user name. This replaces the version table of #2046.
5. **OpenTofu** (#2052). The review of the recent releases is done:
   - **Fetched:** the nightly run of 2026-10-29 ran OpenTofu 1.13.2 (in
     `TestBothToolsSameServer`). The log has no failed `TestCLIs/opentofu`
     step in that run.
   - **Fetched:** release dates from the GitHub releases page of OpenTofu:
     1.12.8 on 14 October, 1.12.9 and 1.13.2 on 21 October. 1.13.0 and 1.13.1
     came on 30 September and 1 October.
   - **Fetched:** the changelogs of 1.13.0, 1.13.1, 1.13.2, 1.12.8 and 1.12.9
     have no entry about the cloud block, the HTTP backend, TFE, login, locks,
     state upload or download, or service discovery. The entries that touch
     workspaces (1.13.0 #4428, 1.13.2 #4706) change only CLI text and shell
     completion. Two entries are security fixes (1.12.8 #4700, 1.12.9 #4751).
   - **Result:** no test change is needed for OpenTofu. The gaps in "What could
     be better" apply to it in the same way.

Because no server change is possible, there is no pull request for the server.

## Lessons

- A "latest" entry is a feature, not a flake. Keep it.
- A deliberate upstream change needs a change in our test. It does not
  need a change in the server. Say so in the first line of the fix, so a
  reviewer does not look for a server bug.
- A signal is only as good as the run around it. A run that is red for one
  known reason cannot show a second reason.
- A record of "what is new" is only as good as its input. The contract
  comparison read reports from tests that the contract did not use, and gave a
  false "new read".

## Context

ADR 216 decision 7 (owner) says: with `access.installationGrantsReachNamespaces` set to `false`, a grant on `@server` gives only the actions of the operator scope and never an action inside a namespace. On main the setting does not exist. The authorizer adds `@server` to the chain of each namespace, collection, unit and namespace principal, and reads no setting. This change adds the setting and makes every reader of the grants follow it.

## Decisions

1. **One declaration.** NEW `SettingInstallationGrantsReachNamespaces = "access.installationGrantsReachNamespaces"` in `pkg/access/settings.go`, next to `SettingCollectionUnitCap`. It is added to `SettingDeclarations()` after the existing entry: kind `setting.KindBool`, level installation, default `"true"`, `Database: true` (the static layer can lock it, so OpenDustpan Cloud locks `false`, ADR 63), `Apply: setting.ApplyLive`, no secret, no `Check` (the bool kind validates the text). `ReducesSecurity(old, next)` is true when `old == "false" && next == "true"`: a change that lets a grant on `@server` reach namespaces needs the fresh authentication that the settings API already asks for. The doc text is in strict STE.
2. **One reading of the value.** NEW exported `InstallationGrantsReachNamespaces(ctx, settings Settings) (bool, error)` in `pkg/access/settings.go`. The type `Settings` is the one that `pkg/access/settings.go` already declares for `ServiceConfig`. A nil `Settings` returns `true`, the declared default (the configs of the conformance suites that do not test the setting have no settings port). A read that fails returns the error, and a value that is not `true` or `false` returns an error. The callers deny on an error (fail closed, step 5 of the rules for security code). The value is read once for each request: the request cache of `pkg/access/cache.go` keeps it, so a decision never reads two different values, and the next request reads the new value (decision 12). `Authorize` and `ListObjects` return the denial and write no audit entry, as for any other denied decision. The caller of `Authorize` (the HTTP handler) writes the one audit entry with the outcome denied.
3. **One place decides the chain.** `chainObjects` (`pkg/access/authorizer.go:921`) takes the reach value in the NEW struct `chainPorts`, as the NEW field `reachesNamespaces` (a bool), and takes no separate bool argument. When it is `false`, the chain of a namespace, a collection, a unit and a principal of a namespace has no `identity.ServerObject()`. The chain of the installation object and of a principal of the installation keeps it, because these objects are in the operator scope. Operator actions are always checked on `@server` or on an installation principal, so they stay allowed through a grant on `@server`. The authorizer (`Authorizer.chain` in `pkg/access/authorizer.go`), the reach (`Reach.chain` in `pkg/access/reach.go`), the access review (`pkg/access/review_service.go`, through the `chain` method of `Authorizer`) and the grant checks (`pkg/access/service.go`, through the same method) all call this function, so they all follow the setting with no second rule.
4. **The scope lists follow the same value.** `ListObjects` and the grant ID discovery read grants through `reachGrants` and `grantInScope`, not through the chain. `grantInScope` returns `false` for a grant on the installation when the value is `false` and the action is not an action of the operator scope (a role that holds a namespace action and a grant on `@server` then lists no namespace). `addToScope` is not changed: it never sees such a grant. With `false`, the wildcard read `namespaces/-` lists only the namespaces of grants on a namespace, a collection, a unit or a principal of a namespace (ADR 216 decision 10). The operator-scope check is `FamilyOf(action) == FamilyOperator` plus the administration actions that ADR 216 decision 3 puts in the operator scope: the test of task 2.2 compares both lists, so a new action cannot go to the wrong side without a failing test.
5. **The bootstrap administrator is not a grant.** `Authorize` returns before it reads any grant when the caller principal has the field `Admin` set (`pkg/access/authorizer.go:123`; ADR 6: the holder of every action on the installation, with no grant). The decision 7 text speaks of a grant on `@server`, so this change does not change the bootstrap administrator and records it as a limit of the setting in `docs/guides/roles-and-grants.md` ("the bootstrap administrator token is not a grant: the setting does not limit it"). No decision of ADR 216 says otherwise, and this change makes none. (Benchmark: the cloud practice of a break-glass account that no tenant setting limits, with an audit entry for each use.)
6. **Support access stays an ordinary grant.** ADR 216 decision 11 gives support access as a grant on the namespace. A grant on a namespace is not a grant on `@server`, so this change needs no code rule for it.
7. **The settings port reaches the authorizer and the reach.** The two free-standing readers build their own `Reach`: `ReachOf` (`pkg/access/reach.go:438`), `GroupReachOf` (`:464`), `Protected` (`:520`) and `ProtectedGroups` (`pkg/access/protected_batch.go:25`) take a `ReachConfig` and return a bool, a map or a `Reach` to the caller. A method on the returned `Reach` would come too late, and the callers (`internal/api/server/principals.go:341` and `:378`, `internal/localusersvc/manage.go:167` and `:172`, `pkg/accesstoken/scope.go:359` and `:381`) could not call it. So the reach takes the setting from its config:
   - `ReachConfig` gets the field `Settings Settings`. `ReachOf`, `GroupReachOf`, `Protected` and `ProtectedGroups` give the NEW field `ReachConfig.Settings` to the `Reach` that they build. `Reach` has an unexported field `settings`, and no settings method.
   - `Settings` is required in a `ReachConfig`. `checkReachConfig` returns `ErrMissingDependency` ("settings") for a nil `Settings`, so a reach with no settings port fails closed and never reads a default `true`. A test that needs a fixed value uses the NEW constructor `access.FixedSettings(reaches bool) FixedSettingsPort` in `pkg/access/settings.go`; `FixedSettingsPort` is an exported type that implements `Settings`; it answers the key of this change with `"true"` or `"false"`, and any other key with the not-found error that the `Settings` port documents for an unknown key.
   - `AuthorizerConfig` gets no new field. NEW `Authorizer` gets the method `WithSettingsPort(Settings) *Authorizer`. It returns a copy that has an unexported `settings` field, so the many literals of `AuthorizerConfig` that name every field (exhaustruct) stay as they are. The method name is not `WithSettings`, because `dustpan.WithSettings` is a different server option. An `Authorizer` with no settings port uses the default `true` (decision 2). The copy of the authorizer that `Service.within` (`pkg/access/check.go`) builds for the transaction of a write takes the same settings port, with the chain that the Service read before the write.
   - The `Settings` implementation is the one that `pkg/dustpan/dustpan.go` builds for `ServiceConfig`. The two `access.NewAuthorizer` calls of that file are followed by a call of the NEW method `Authorizer.WithSettingsPort` with it; the construction of the reader moves before them, because the authorizer is built first on main. Each production `ReachConfig` literal sets `Settings` with the same reader: `cmd/opendustpan/host.go`, `pkg/dustpan/localusers.go` (lines 287 and 299), `pkg/access/protected_batch.go` (`reachCache.config`, line 207), `e2e/coverage_server.go` and `e2e/coverage_signin.go`.
   - Why a field and not a method: exhaustruct forces every one of the 91 `ReachConfig` literals on main (52 files) to name the field, so no caller can build a reach and skip the setting. A new caller that forgets it does not compile. This is the structure that makes the bug class impossible, in place of a check.
8. **Hosted installations.** The static layer locks `false` in OpenDustpan Cloud (outside this change, per "Out of scope" in the proposal). A self-hosted installation that sets `false` ends the access of each installation person in a namespace, except the grants on that namespace (ADR 215 decision 11). The effective value and its source show in `GET /api/dustpan/v1/settings` like any setting, so a person can ask why a namespace action was denied (No magic).
9. **The principal routes follow the setting.** The routes of `internal/api/server/principals.go` (`Handler.principalRoutes`) authorize `server:manage-principals` and `server:read-principals` on `@server`, and the service in `pkg/principal/service.go` checks no namespace. So, with the setting `false`, a caller that holds only a grant on `@server` would still list and change the service principals of a namespace. ADR 216 decision 7 says that a grant on `@server` gives no action inside a namespace. With `false`, these routes refuse a principal of a namespace (namespace not empty): the answer is 403 that names the action and "on this namespace", as the shared 403 rule does, with one audit entry with the outcome denied. The list returns only the principals of the installation (namespace empty). With `true`, nothing changes. Two layers, and each stops the case alone:
   - Handler layer: after the handler resolves the target principal, a NEW helper `Handler.refuseInstallationReach` in `internal/api/server/principals.go` refuses a principal of a namespace. It reads the value through the NEW method `Authorizer.GrantsReachNamespaces` (below). It covers get, change, delete, enable, disable and the groups of a principal. A failed read denies (fail closed).
   - Service layer: `pkg/principal` cannot import `pkg/access`, because `pkg/access` imports `pkg/principal`. So the value reaches the service through a NEW port. NEW interface `InstallationReach` in NEW `pkg/principal/installation_reach.go` has one method, `GrantsReachNamespaces(ctx context.Context) (bool, error)`. NEW method `Service.WithInstallationReach(InstallationReach) *Service` returns a copy that has the port, so the literals of `Config` stay as they are. NEW method `Authorizer.GrantsReachNamespaces(ctx context.Context) (bool, error)` in `pkg/access/authorizer.go` reads the value with the reader of decision 2 through the settings port of the authorizer, so the `Authorizer` meets the port with no import. A `Service` with no port uses `true` (decision 2). The wiring in `pkg/dustpan/dustpan.go` always gives the port (decision 11).
   - The methods of the service that the `@server` routes call, `UpdatePrincipal`, `DeletePrincipal`, `EnablePrincipal` and `DisablePrincipal` (`pkg/principal/service.go`), read the principal and return an error that wraps `identity.ErrDenied` for a principal of a namespace when the value is `false` or cannot be read. The methods of a namespace, `UpdateNamespacePrincipal` and `DeleteNamespacePrincipal` (`pkg/principal/namespace.go`), call NEW unexported twins of these methods that do not read the value, because their caller is authorized on the namespace and not on `@server`. Main has no other caller of the four methods.
   - The list: the field `Query.InstallationOnly` (a bool) in `pkg/principal/page.go` keeps the principals with the namespace empty. `Service.ListPrincipals` sets it when the value is `false`. The two store adapters add one condition to the queries `ListPrincipals` and its count in `internal/store/sqlite/queries.sql` and `internal/store/postgres/queries.sql`, and regenerate with `make generate`; the conformance suite `pkg/principal/principaltest` gets one case for the field. The preflight PR adds `Query.InstallationOnly` to `principal.Query` in every existing literal; this change does not touch those files. The total of the page counts only the principals that the page can show.
10. **The token managers follow the setting.** `Service.principalReviewScope` (`pkg/access/review_service.go:735`) always gives the scope of the export of a service principal the container `@server`, also for a principal of a namespace. So `TokenManagers`, the membership audit entry (`pkg/principal/service.go:546`) and `withTokenManagers` (`pkg/access/service.go:1343`) name holders of a grant on `@server` as token managers of a namespace principal, and the authorizer then refuses them with `false`. With `false` and the namespace of the principal not empty, the scope leaves `@server` out of `Containers`. With `true`, and for a principal of the installation, `@server` stays.
11. **The production wiring always passes the settings port.** `newAccessService` (`pkg/dustpan/dustpan.go:3486`) leaves `settings` nil when the settings service is nil, and a nil port means `true` (decision 2). So a deployment that loses the settings service would reach namespaces with no message. The wiring builds the settings service before the authorizer, and `newAccessService` returns an error when it gets none, so the built server never has a nil port. A test in NEW `pkg/dustpan/installation_reach_internal_test.go` builds the server, stores the value `false`, and checks that the authorizer of the built server denies a grant on `@server` for a namespace action. `NewServer` refuses a built-in store (`WithSQLite`, `WithPostgreSQL`, `WithBuiltinStore`) when the caller gave no `WithSettings`. `WithSQLite` and `WithPostgreSQL` open the store inside `NewServer`, so the caller cannot give `WithSettings` with them. The error names the fix: open the store with `OpenStore`, pass it with `WithBuiltinStore`, and add `WithSettings`. The tests of the built-in stores and `docs/reference/sdk.md` use that form.
12. **Read once per request.** The value of the setting is read at most once for each request. `InstallationGrantsReachNamespaces` (decision 2) reads the store on the first call in a request, and keeps the answer in a request-scoped value: the context key that the request cache of `pkg/access/cache.go` already uses, declared in `pkg/access/settings.go` next to the reader. Every later authorization, `ListObjects`, reach and access review call in the same request takes that value and makes no read. A request that has no request cache reads the store at each call, so it never holds a stale value. There is no cache across requests, no timer and no shared field on the `Authorizer`: the value dies with the request. A change of the setting between two requests is seen by the second request, as the row "A change of the setting between two requests" of the table "Layers" requires. A failed read is not kept: the error denies the decision and the next call in the request reads again. Why: a read for each authorization adds 1 to 2 round trips to each authorized call, and the budgets of `internal/servertest` count them (task 2.6). One read of a setting through the settings service is 2 statements (`ListSettings` and `GetSettingsState`), so one read for each request costs 2 round trips for each authorized request (`reachSettingReadTrips = settingReadTrips = 2`), and it is the only read of the reach setting that an authorized request adds. A backup holds no read of the reach setting (`backupModel` adds 0). Measured on PostgreSQL: a plain restore adds 2, and a restore with one failed swap adds 6: the 2 of the plain restore and 4 of the swap decision. Each swap decision runs two readers, `readAccessSetting` and `accessSettingIsStatic`, of 2 statements each, so `swapRetryTrips` gets the term `swapAccessSettingReadTrips = 2 * settingReadTrips`. The restore reads run in `stepSwap` (`pkg/backup/restore_steps.go`) through `swapDecision` (`pkg/backup/restore_access_setting.go`), which calls `readAccessSetting` and `accessSettingIsStatic`; these call `Effective` in `pkg/dustpan/settings_resource.go`. `internal/servertest/servertest.go` passes no `WithSettings` today, in the branch for the built-in store (`WithBuiltinStore`) and in the branch with one option for each port (`WithUnitSettingsStore`); task 2.5 adds it to both.

## Contract

New names in `pkg/access` (each is NEW on main):

- `SettingInstallationGrantsReachNamespaces = "access.installationGrantsReachNamespaces"`, a constant in `pkg/access/settings.go`.
- `InstallationGrantsReachNamespaces(ctx context.Context, settings Settings) (bool, error)`, in `pkg/access/settings.go`. It returns `true` for a nil `settings`, and an error for a failed read or a value that is not `true` or `false`.
- The request-scoped value of decision 12: an unexported context key in `pkg/access/settings.go`, set by the request cache of `pkg/access/cache.go`, and read only by `InstallationGrantsReachNamespaces`. It has no exported name and no cache across requests.
- `(*Authorizer).WithSettingsPort(Settings) *Authorizer`. It returns a copy.
- `ReachConfig.Settings Settings`, a required field (decision 7). A nil value makes `ReachOf`, `GroupReachOf`, `Protected` and `ProtectedGroups` return `ErrMissingDependency`.
- `FixedSettings(reaches bool) FixedSettingsPort`, in `pkg/access/settings.go`: `FixedSettingsPort` is an exported type that implements `Settings`. It gives a fixed value of the setting for a test and for a fixed deployment.
- `chainObjects` takes the NEW field `reachesNamespaces` in the NEW struct `chainPorts`: no new argument.
- `(*Authorizer).GrantsReachNamespaces(ctx context.Context) (bool, error)`, in `pkg/access/authorizer.go` (decision 9).
- NEW unexported function `confineInstallationGrants` in `pkg/access/authorizer.go`: after the chain, it drops a grant on `@server` for an action that acts inside a namespace when the value is `false`. It is a defense-in-depth layer: the chain (decision 3) and `grantInScope` (decision 4) each stop the case alone, and this check does not rely on them.
- NEW in `pkg/principal`: the interface `InstallationReach` and the method `Service.WithInstallationReach` (decision 9). The field `Query.InstallationOnly` comes from the preflight PR.

Endpoints: none new. The setting uses `GET /api/dustpan/v1/settings` and `PATCH /api/dustpan/v1/settings`, which main has. A refused read of the setting is an error that the decision returns as a denial. A denial in a namespace answers 403 with the action and the kind of the object ("on this namespace"), as the shared 403 rule does. It does not name the namespace, because a 403 that named the object would tell a caller without access that the object exists. A `PATCH` from `false` to `true` with an access token answers 403 `mfa.fresh-step-required`.

Tables, schema and CLI output: no change.

## Structure

- One function decides the chain, one function reads the value. No second rule in the review, the reach or the service.
- The setting is read through the port that the Service already has. No new dependency and no new tool.

## Layers

Security code: each layer has its own table of hostile cases, and each guard has a test that fails when the guard is removed.

| Layer | Hostile case | Expected |
| --- | --- | --- |

| Service (`pkg/dustpan`) | The built server, value stored `false`, a grant on `@server` for a namespace action | denied: the authorizer reads the stored value |
